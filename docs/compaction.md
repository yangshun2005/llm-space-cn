# 对话压缩

对话压缩会将较早的对话轮次替换为结构化检查点，同时保持最近的对话轮次不变。这对于长时间运行的线程中已积累的上下文仍然重要但不再需要逐字发送给模型的情况非常有用。

LLM Space 将压缩实现为一种预览优先、渐进式的工作流程。原始线程永远不会被覆盖：应用压缩会在其旁边创建一个新线程。

## 使用压缩

1. 打开一个至少包含两个用户轮次的线程。
2. 打开线程标题中的 **更多操作** (`...`) 菜单。
3. 选择 **压缩对话**。
4. 阅读介绍，然后选择 **下一步**。
5. 配置要逐字保留的最近对话轮次数。可选地，为检查点必须保留的事实或决策添加压缩指令。
6. 选择 **开始压缩**。LLM Space 渲染提示变量并生成实时检查点预览。此时线程尚未更改。
7. 审查预览。如有必要可重新生成，或选择 **应用压缩** 以创建压缩副本。

压缩后的线程会与源线程并列写入，并在新标签页中打开。其名称使用递增后缀：

```text
feature-design.json
feature-design-compact-1.json
feature-design-compact-2.json
```

对 `feature-design-compact-2.json` 再次压缩会继续相同的序列，而不会产生嵌套名称。

## “保留最近对话轮次”的含义

一个对话轮次以用户消息开始，并包含其后的助手响应和工具活动。如果线程有八个轮次且 **保留最近对话轮次** 设置为三，则前五个轮次将合并为一个检查点，最后三个轮次保持逐字不变。

```text
压缩前                              压缩后
┌──────────────────────────┐        ┌──────────────────────────┐
│ 较早的轮次 1             │        │ 结构化检查点             │
│ 较早的轮次 2             │        │ (轮次 1–5)               │
│ 较早的轮次 3             │   →    ├──────────────────────────┤
│ 较早的轮次 4             │        │ 最近的轮次 6 (原样)      │
│ 较早的轮次 5             │        │ 最近的轮次 7 (原样)      │
│ 最近的轮次 6–8           │        │ 最近的轮次 8 (原样)      │
└──────────────────────────┘        └──────────────────────────┘
```

界面始终在检查点之外至少保留一个真实的对话轮次，以便新线程保留一个逐字的延续点。

## 压缩指令

可选的 **压缩指令** 字段会向摘要器添加线程特定的指导，例如：

```text
保留确切的文件路径、API 决策、未解决的错误以及用户的 UI 偏好。
```

指令保存在 `thread.meta.compactionInstructions` 中。下次压缩该线程时会重复使用这些指令，但它们不会添加到普通的模型运行中。

## 生成的消息布局

检查点是一个包装在系统提醒中的合成用户消息：

```xml
<system-reminder>
之前的对话已压缩到下面的检查点中。将其作为上下文以继续任务；这不是新的用户请求。

# 上下文检查点

## 目标
...
</system-reminder>
```

完整的消息顺序为：

1. 元用户提示（如果线程有的话）。
2. 合成的压缩检查点。
3. 配置数量的最近对话轮次，保持不变。

当不存在元用户提示时，检查点将成为第一条用户消息。这可以将可复用的运行时指令保持在检查点之前，而不会将它们误认为对话历史。

## 渐进式压缩

压缩是渐进式的而非破坏性的。当压缩后的线程再次被压缩时，LLM Space 会将先前的检查点和新过期的轮次一起发送给摘要器。模型会更新检查点，保留仍然相关的目标、约束、决策、路径、错误和进度，而最近的轮次则继续在逐字窗口中移动。

```text
第一次压缩：   [轮次 1–5]        → 检查点 A + 轮次 6–8
下一次压缩：   [检查点 A + 6]    → 检查点 B + 轮次 7–9
```

现有检查点消息 ID 会在克隆线程中被重用，因此它被视为一个不断演进的检查点，而不是额外的对话轮次。

## 实现

压缩语义属于 LLM Space，而非 pi-agent-core 压缩 API：

- `packages/core/src/thread/compaction.ts` 识别轮次边界，分离可摘要和保留的跨度，序列化消息和工具活动，构建摘要器提示，检测先前的检查点，并重建最终的消息列表。
- `packages/ui/src/components/thread-playground/thread-compaction-dialog.tsx` 实现三步向导、指令持久化、提示渲染、流式预览和确认流程。
- `packages/ui/src/components/thread-playground/use-stream-text.ts` 通过常规的 LLM Space 流式传输发送摘要器请求。
- `apps/desktop/src/components/thread-tabs/thread-tab-pane.tsx` 在确认后写入并打开压缩后的克隆。

提示变量、启用的技能和包含的文件会在对话序列化之前进行渲染。这可以防止诸如 `{{current_date}}` 之类的原始占位符泄漏到检查点提示中。工具结果包含在每个结果的大小上限内，图像附件则通过其数量来表示，而不是嵌入二进制数据。

最终的模型请求仍然通过现有的代理流式传输栈进行传输，其桌面后端使用 pi-agent-core 的通用代理循环。换句话说，pi-agent-core 执行底层模型运行；LLM Space 负责压缩规划、提示、渐进式检查点语义、预览和消息转换。

## 预览和应用保证

- 打开向导不会启动模型请求。
- 更改选项不会修改线程。
- 开始压缩仅生成预览。
- 关闭或取消向导会保持消息不变。
- 应用会创建一个新的 `-compact-N.json` 线程；源文件保持不变。
