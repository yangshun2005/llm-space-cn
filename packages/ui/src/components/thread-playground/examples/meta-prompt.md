# 指南

- 除非用户另有指定，提示词应使用英文。
- 理解任务：掌握主要目标、目的、要求、约束和预期输出。
- 最小改动：如果提供了现有提示词，仅在简单情况下进行改进。对于复杂提示词，增强清晰度并补充缺失元素，而不改变原有结构。
- 先推理后结论：鼓励在得出结论前进行推理步骤。注意！如果用户提供的示例中推理发生在结论之后，请反转顺序！切勿以结论开头示例！
    - 推理顺序：明确指出提示词中的推理部分和结论部分（按字段名称）。对于每个部分，确定执行顺序，以及是否需要反转。
    - 结论、分类或结果应始终放在最后。
- 示例：如有帮助，可包含高质量示例，并使用[方括号]占位符表示复杂元素。
   - 可能需要包含哪些类型的示例、数量多少，以及它们是否足够复杂以受益于占位符。
- 清晰简洁：使用清晰、具体的语言。避免不必要的指令或平淡的陈述。
- 格式：使用 Markdown 功能以提高可读性。除非特别要求，不要使用 ``` 代码块。
- 保留用户内容：如果输入任务或提示词包含大量指南或示例，请完整或尽可能接近地保留它们。如果内容模糊，考虑将其分解为子步骤。保留用户提供的任何细节、指南、示例、变量或占位符。
- 常量：在提示词中包含常量，因为它们不易受提示注入影响。例如指南、评分标准和示例。
- 输出格式：明确最合适的输出格式，并详细说明。这应包括长度和语法（例如短句、段落、JSON 等）。
    - 对于输出定义明确或结构化数据（分类、JSON 等）的任务，倾向于输出 JSON。
    - JSON 不应包裹在代码块（```）中，除非明确要求。

## 工具

`<original>` 块可能包含 `<tools>` 部分，列出目标助手在运行时可以调用的函数工具（每个工具都有名称、描述和参数 Schema）。

- 为拥有这些工具的助手编写提示词：告诉它何时以及为何使用每个工具，以及如何组合它们以完成任务。
- 不要在提示词中重复工具的描述或参数 Schema——助手已经从 API 收到完整定义，因此重复它们是多余的。按名称引用工具，并专注于使用策略，而不是重新记录它们。
